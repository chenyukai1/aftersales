## 4. 领域模型（DocType 一览）

### 4.1 主数据（字典/档案）
| DocType | 说明 | 备注 |
|---------|------|------|
| Vehicle Delivery | 整车发货（车辆档案） | 含购车客户/对接人（登记自动带出源） |
| Spare Part | 配件主档（K3 编码/E10 品号/供应商/索赔需求/ERP 物料） | 登记带出 + M1 出库物料 + M2 判定 + M3 清单核心 |
| Supplier | 供应商（ERPNext 标准） | 导入自动创建 |
| Customer / Contact / Address | 客户主档 + 主联系人 + 主地址 | 登记选客户预填收货（标准表） |
| Special Part Registration | 特殊配件登记（订单号/跟踪状态） | 铭牌带出 #37 |
| Fault Category / Part / Phenomenon | 故障字典（三级） | 登记三级点选 |
| After Sales Option | **可编辑枚举**（option_type + option_value + 序号） | 下拉选项后台维护 |
| Improvement Record | 改进记录（改进-再发比对） | — |

### 4.2 业务单据
| DocType | 说明 | 生命周期 |
|---------|------|---------|
| **Service Request** 售后登记 | 主表 + Service Part Item 子表(配件行) | 草稿→待审批→**已通过**(提交自动联动)/已驳回 |
| **Claim Order** 索赔单 | M1，服务单自动创建，挂配件明细 | 草稿 → 出库 → 完成 |
| **Delivery Note** 出库单 | ERPNext 标准，由索赔单"生成出库单"创建 | 提交后回写索赔单/登记状态 |
| **Old Part Recall** 旧件追回 | 按登记"需提供旧件"自动建，含 Reminder 子表 | 追回提醒→已追回/60 天超时终止 |
| **Claim List** 供应商索赔清单 | 按月 + 按供应商汇总（M3） | 月度自动生成，采购可编辑确认 |
| **Quality Issue Closure** 质量闭环 | 五阶段：定性/吹哨/批量/评审/方案落地 | 批量隐患自动触发或人工创建，标记完成闭环 |
| **Quality Issue Action** 改进行动 | 闭环方案落地行动项 | 与改进记录衔接 |

### 4.3 单据间自动联动（hooks / doc_events）
```
售后登记提交(审批通过 on_submit)
 ├─ 创建 Claim Order（草稿索赔单，带配件行）
 ├─ 创建 Old Part Recall（need_return=是 的配件 → 追回提醒）
 ├─ 批量隐患(售后类型) → 自动创建 Quality Issue Closure（_auto_classify 定性）
 ├─ Improvement Record 命中 → 评论"改进-再发"提醒
 ├─ OA 状态回写（特殊申请→Y） + 外发事件 service_request.approved（预留）
Delivery Note on_submit → 回写 Claim Order 状态 + 登记 ERP录入=OK
File on_update → 归档到 售后资料/{车型}/{YYYY-MM}/{部件}
daily_long 调度 → 旧件追回提醒/超时 + 批量隐患扫描
cron 每月1日2点 → 生成上月 Claim List
```

所有命令均在容器内 bench 环境执行（宿主机 git bash 只做 git）：


| 场景 | 命令 |
|------|------|
| 浏览器访问 | http://127.0.0.1:18090（账号见 §5，管理员 Administrator） |

| 灌演示数据（幂等） | `bench --site dev.localhost execute "frappe.get_attr('aftersales.after_sales.seed.run')()"` |
| 上线/演示前就绪体检 | `bench --site dev.localhost execute "frappe.get_attr('aftersales.after_sales.setup_check.run')()"`（输出 ✅/⚠️/🔴 分级报告） |

## 11. 已踩坑记录（Frappe 16 / 本环境）——改代码前必读

| # | 坑 | 解法 |
|---|----|------|
| 1 | DocPerm 不设权限位时**默认全 1（全开）** | `_perm_row` 显式设每一位 + "先删后建"保证幂等 |
| 2 | Frappe 16 Workflow：无 doc_status 布尔，改字符串 "0"/"1"；`allow_edit` 必填角色；`transition.state` Link 需 `ignore_links=True` | 见 create_service_request_workflow |
| 3 | workflow_state 字段自动建为 Link，按状态名 Link 校验失败 | 改为 **Data 类型**（setup 内已处理） |
| 4 | `owner` 是 Frappe 保留字段 | 改用 `owner_person` |
| 5 | Select 字段**自动填首选项**，导致状态误判 | 加其它条件判定（如 review_date） |
| 6 | 子表/改进记录数据跨连接不可见 | 需 `frappe.db.commit()` |
| 7 | 容器改 DocType → 源码 json 被同步改写 | 正常，一并 git 提交 |
| 8 | Date 字段读回是 date 对象，与 isoformat 字符串比较恒不等 → 导入永不收敛 | 归一化比较 `_neq()` |
| 9 | Address.city 为 reqd，直辖市/无"省市"字样地址会报 MandatoryError | city 兜底 = 地址粗提取 or state or "其他" |
| 10 | Single DocType 加字段后 migrate 较慢（约 5~10 分钟） | 正常，等 `EXIT=0` |
| 11 | Docker Desktop 引擎：wsl.exe 曾进程序黑名单 + 沙箱缺 ProgramData/APPDATA 导致崩溃 | 用户手动从桌面启动 Docker；不要用沙箱代启动 |
| 12 | bench 命令必须用容器 venv python 跑测试脚本 | `./env/bin/python apps/aftersales/test_all.py`（裸 python 会缺依赖） |
